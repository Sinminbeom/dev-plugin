# Python 코딩 컨벤션

SOLID 원칙을 기본으로 한다.

## 클래스 래핑

서로 관련된 함수 2개 이상은 모듈 레벨 전역 함수 대신 클래스로 묶는다.

- **상태 없음** → `@staticmethod` 유틸리티 클래스
- **상태 있음**(주입 의존성·설정) → 인스턴스 헬퍼. 역할이 분명하면 관례적 역할 이름 우선 — 비즈니스 로직 `~Service`, 데이터 접근 `~Repository`, 외부 연동 `~Client`. 이런 역할에 안 들어맞는 보조 로직 묶음만 `~Helper`
- 단일 함수·한 곳에서만 쓰는 사소한 헬퍼는 억지로 클래스화하지 않는다
- 코드베이스에 정적 유틸리티 클래스 선례가 있으면 그 스타일에 맞춘다
- 클래스 종속 **상수/정책값**은 모듈 전역이 아니라 그 클래스의 클래스 상수로 둔다 (예: `GroupService.MAX_GROUP_DEPTH`)
  - 고정 정책값은 config/env로 빼지 않는다. 런타임·환경별로 달라져야 할 때만 설정으로 외부화한다

## 다중상속 정책

- 상태(state)를 가진 일반 클래스의 다중상속 **금지** — 메서드가 어느 부모 구현으로 해석되는지 선언 위치에서 보이지 않아(MRO가 결정론적이어도 코드에 드러나지 않음) 리뷰·디버깅 비용이 비대칭적으로 증가한다. "한 파일을 열었을 때 그 동작을 예측할 수 있어야 한다"
- 인터페이스(`Protocol`/`ABC`) 다중상속은 **허용** — 구현/상태가 없으므로 가시성 문제가 없다

## 타입 네이밍

식별자만 보고 인터페이스/추상/구체를 구분한다. PEP 8 관습과 어긋나더라도 이 규칙을 우선한다.

| 카테고리 | 표기 | 예시 |
| --- | --- | --- |
| 일반 클래스 | `PascalCase` | `UserRepository` |
| 인터페이스 (`Protocol`·순수 계약 `ABC`) | `I` + PascalCase | `IUserRepository` |
| 추상 클래스 (부분 구현 `ABC`, 상속 전제) | `ab`(소문자) + PascalCase | `abUserRepository` |
| 상수 | `UPPER_SNAKE_CASE` | `MAX_RETRY_COUNT` |

- 구현체는 접두사 없이 구체적인 이름을 쓴다 (`IStorage` / `abStorage` ← `S3Storage`)
- 구체 구현이 하나뿐이거나 단순 데이터 홀더(`dataclass` 등)는 추상화가 아니므로 접두사를 붙이지 않는다
- prefix 대소문자가 비대칭인 이유: 단일 문자 `I`는 PascalCase에 자연스럽게 녹아들지만, 다중 문자 `ab`는 소문자로 두어야 prefix임이 시각적으로 명확하다

## 주석·docstring

**코드는 WHAT을 말하고, 주석은 WHY를 말한다.** 대부분의 클래스·함수는 docstring·설명 주석 없이 작성하고, 이름과 타입 시그니처가 의도를 드러내게 한다.

주석은 코드만 봤을 때 "왜 이렇게 했지?"라는 질문이 나올 곳에만 단다.

| 케이스 | 예시 |
| --- | --- |
| 외부 시스템·라이브러리 제약 | `# Stripe API는 amount를 cents 단위로 받음` |
| 일견 이상해 보이지만 이유가 있는 코드 | `# v1 API 호환성 위해 null도 허용` |
| 일반적 방법과 일부러 다르게 짠 부분 | `# set 대신 list — 입력 순서 보존 필요` |
| 지우면 안 되는 이유가 비자명 | `# 이 라인 제거하면 macOS에서 path 인코딩 깨짐` |

- 공개 API(라이브러리·패키지 사용자에게 노출되는 시그니처)는 docstring 권장
- WHAT을 반복하는 주석 금지 — 이름이 이미 말하는 내용을 다시 적지 않는다
